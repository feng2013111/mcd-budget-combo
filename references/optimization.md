# 优化引擎设计说明

`scripts/optimize_combo.py` 把「预算内怎么点最好」建模为**带约束的组合枚举 + 启发式评分**问题。本文说明评分模型、枚举策略与优惠券匹配逻辑，以及所有已知局限。

## 一、数据模型

- **Item**：`code`（MCP 商品标识）、`name`、`price`（内部统一用「分」）、`category`（归一化为 staple/snack/drink/dessert/combo）、`taste`（口味分 0-10）、`value`（满足感分值）。
- **Coupon**：`kind` 为 `threshold`（满减，带 `min_spend` 门槛）或 `product`（指定商品，带 `product_codes` 名单）；`discount` 单位为分。

金额归一化策略（`_price_to_fen` / `_coupon_money_to_fen`）：

- 菜单价：字符串按「元」（`query-meals` 实际返回 `"25.5"` 这种字符串）；数值 ≥1000 视为分、<1000 视为元；
- 券金额：数值 <100 视为元，其余视为分（与「MCP 金额单位为分」的社区实测口径对齐）。

## 二、评分模型（启发式，非官方数据）

**满足感 `value`**：按品类给基础分（主食 10 / 小食 7 / 饮料 5 / 甜品 6 / 套餐 14），用户偏好关键词命中 +2。用途：性价比与省钱模式的「吃到多少东西」度量。

**口味分 `taste`**：内置常见单品的粗略大众向评分（如薯条 8.5、麦辣鸡腿堡 8.5、可乐 7.0），未覆盖的按品类默认分；匹配时先精确、再子串（兼容「可乐（中）」这类规格后缀），用户偏好关键词 +1.5（封顶 10）。

> ⚠️ 这两套分**不是麦当劳官方数据，也不是真实测评**，只是让「性价比」「好吃」可排序的代理指标。用户偏好（`--prefer` / `--exclude`）永远优先于内置表。

## 三、组合枚举

按「一顿像样的餐」的结构约束生成候选（`MEAL_SHAPE`：主食 1-2、小食 0-2、饮料 0-2、甜品 0-1、套餐 0-1）：

1. 每个品类按排序键（性价比模式用 `value/price`，好吃模式用 `taste/price`）取前 8 个；
2. 品类内展开 0/1/2 件的选择，跨品类做笛卡尔积；
3. 用预算与总件数剪枝（`--max-items`，默认 5）。

菜单约百款、每品类取 Top-8 时，候选量在数千级，Python 纯标准库可秒出。若菜单异常庞大，调小 `top_k`（代码内常量）即可。

## 四、三种模式

| 模式 | 目标函数 | 额外约束 |
| --- | --- | --- |
| `value` | 最大化 `value_sum / 券后实付（元）` | 组合须「像一顿餐」：≥2 件或含套餐类单品 |
| `taste` | 最大化 `taste_sum`，同分比实付更低 | 无 |
| `save` | 满足感 ≥ 12（约「主食+小食」）中实付最低 | 无 |

## 五、优惠券匹配（保守策略）

对每个候选组合挑**一张**最优券：

- 满减券：原价 ≥ `min_spend` 时可用，折扣按 `min(discount, 原价)` 计；
- 商品券：组合包含券指定商品时可用，**按一张计一次折扣**（不假设按件数叠加）；
- 门店券：`store_code` 不匹配当前门店时跳过。

**为什么不自动叠加**：麦当劳 MCP 未文档化券的叠加规则，社区实测确认 `query-promotions` 对个人用户不可用。叠加假设会让估算价偏离真实核价，因此只取单张最优券，并始终提示用户以 `calculate-price` 为准。

## 六、已知局限

1. 口味分是启发式，无法代表真实口味；已在输出中标注；
2. 未处理「限时供应」（如早餐时段菜单）——`now-time-info` 可查时间，但菜单的时段字段官方未文档化，暂不过滤；
3. 外送与堂食价差、配送费未建模（`calculate-price` 的 `orderType` 可区分，核价时需传对）；
4. 组合枚举是启发式 Top-K，不保证全局最优；对预算内的精确最优，可在缩小品类池后用动态规划求解（菜单规模下暂不需要）。
